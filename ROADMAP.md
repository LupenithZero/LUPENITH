# Roadmap

This roadmap is a set of proposed milestones, not a promise of delivery. Priorities may change after public feedback. Work should remain small enough to finish and evaluate.

## Phase 0 — Make the project understandable

- [x] Publish an initial README and draft documents.
- [ ] Decide whether the working title should remain or be replaced.
- [ ] Collect criticism on the charter and governance model.
- [ ] Add sources for major factual claims.
- [ ] Publish a changelog of material document revisions.
- [ ] Define a public decision process for accepting changes.

**Exit criteria:** a newcomer can explain the purpose, current limits, and contribution process without contacting the founder.

## Phase 1 — Build a useful public knowledge resource

- [ ] Pick one narrowly scoped topic, such as evaluating public claims or learning privacy basics.
- [ ] Create a referenced guide in plain language.
- [ ] Have at least two independent reviewers check factual claims.
- [ ] Translate the guide only after the source version is reviewed.
- [ ] Collect feedback and publish corrections.

**Exit criteria:** people outside the project can use the guide without joining the community.

## Phase 2 — Establish a healthy contributor workflow

- [ ] Add clear issue labels and review responsibilities.
- [ ] Establish a published conflict-of-interest statement.
- [ ] Develop a contribution recognition policy that does not imply promised payment.
- [ ] Write a process for appeals and maintainer disputes.
- [ ] Test accessibility and translation workflow.

**Exit criteria:** contributors know how decisions are made and how to challenge them.

## Phase 3 — Complete a small open-source technical project

- [ ] Gather problem statements from users and open-source communities.
- [ ] Compare existing tools before choosing a new build.
- [ ] Select one small deliverable with a maintainer, test plan, license, and realistic scope.
- [ ] Document the threat model if privacy or security is involved.
- [ ] Publish a working prototype or a useful upstream contribution.

**Exit criteria:** the deliverable is usable or independently reviewable and has a maintenance plan.

## Phase 4 — Professional review and social benefit pilots

- [ ] Invite qualified reviewers for public mental-health education.
- [ ] Develop a referral and correction policy for health-related content.
- [ ] Obtain appropriate legal, privacy, finance, and safeguarding advice before running services.
- [ ] Test a small skills-sharing or employment-information pilot without promises of jobs.

**Exit criteria:** risks and limitations are documented, and participants can leave without penalty.

## Phase 5 — Sustainable organization

Only after evidence of demand and reliable contributors:

- [ ] Assess whether formal legal registration is useful and lawful.
- [ ] Design a transparent budget and independent review process.
- [ ] Consider earned-revenue projects or cooperatives.
- [ ] Define election, term, recall, amendment, and conflict-of-interest rules.
- [ ] Consider a local social-support partnership after qualified safeguarding review.

## Long-term aspirations (not current products)

- Privacy-respecting browser improvements or tools.
- A federated or community-controlled video ecosystem.
- Open operating-system or infrastructure contributions.
- Global multilingual learning resources.
- Skills and employment networks.
- Sustainable support for children and young people through properly safeguarded programs.

These aspirations are not commitments to build every item. The project should support existing open-source efforts when that is more useful than creating a competing product.
